# 用户故事与验收标准

## 1. 优先级定义

- P0：MVP 必须实现；
- P1：完善项目体验和工程深度；
- P2：展示性增强功能。

## 2. Epic A：产品与流程问答

### US-A01 查询申请条件（P0）

作为游客，我希望询问某个贷款产品的申请条件，以判断自己是否适合申请。

验收标准：

- 能识别产品名称及常见别名；
- 回答仅使用当前生效、允许对客展示的知识；
- 答案展示主要条件和知识来源；
- 产品不明确时先澄清，不拼接不同产品的信息；
- 不承诺“一定通过”或具体额度。

### US-A02 多轮咨询（P0）

作为客户，我希望继续追问“它最长可以分多少期”，系统能够理解“它”指上一轮产品。

验收标准：

- 会话中保存当前产品和话题；
- 新问题与前文冲突时优先澄清；
- 切换产品后不继续使用旧产品过滤条件。

### US-A03 无答案处理（P0）

作为客户，我希望系统在无法确认时诚实说明，而不是编造答案。

验收标准：

- 低检索置信度时不生成确定性答案；
- 给出澄清问题或人工入口；
- 后台记录未命中问题，供知识运营补充。

## 3. Epic B：申请服务

### US-B01 查询申请进度（P0）

作为已登录客户，我希望查询本人的贷款申请进度。

验收标准：

- 未登录时引导登录；
- 只能查询当前用户的申请；
- 返回申请状态、更新时间和待办事项；
- 无申请记录时明确说明，不生成虚假申请；
- 工具调用和结果写入审计日志。

### US-B02 查询缺失资料（P0）

作为申请中的客户，我希望知道还缺哪些资料以及如何补交。

验收标准：

- 缺失资料来自申请系统；
- 操作说明来自当前流程知识；
- 不展示内部审核意见和反欺诈规则；
- 补件入口使用固定业务链接或前端动作。

### US-B03 审批结果解释（P1）

作为未通过审批的客户，我希望获得可披露的原因说明及复核入口。

验收标准：

- 只解释业务系统返回的合规原因码；
- 不推测内部模型得分和反欺诈规则；
- 提供人工复核或重新申请指引；
- 高风险或争议表达自动升级工单。

## 4. Epic C：账单与还款

### US-C01 查询下一期账单（P0）

作为已登录客户，我希望知道下一期应还金额和还款日期。

验收标准：

- 查询前验证贷款属于当前用户；
- 金额和日期原样取自账单工具；
- 返回本金、利息、合法费用及合计；
- 模型不得自行计算或修改金额；
- 多笔贷款无法确定时要求客户选择。

### US-C02 查询还款记录（P0）

作为客户，我希望查询某笔贷款的历史还款记录。

验收标准：

- 支持按贷款与时间范围查询；
- 银行卡仅展示尾号；
- 查询结果分页或限制最大条数；
- 不在模型上下文中传递完整银行卡号。

### US-C03 提前结清试算（P0）

作为客户，我希望知道指定日期提前结清需要支付多少。

验收标准：

- 试算由 Java 领域服务完成；
- 返回剩余本金、利息、费用、合计和有效期；
- 客户未提供日期时进行澄清；
- 试算不等同于实际结清；
- 项目首版不执行真实支付。

### US-C04 还款未入账（P0）

作为已经还款的客户，我希望确认为什么账单仍显示未支付。

验收标准：

- 分别查询支付流水和账单状态；
- 支付成功但账单未更新时创建高优先级工单；
- 使用幂等键避免重复创建相同工单；
- 明确给出工单号和预计处理方式；
- 不要求客户在聊天中发送完整银行卡信息。

## 5. Epic D：投诉与人工服务

### US-D01 随时转人工（P0）

作为客户，我希望在机器人无法解决问题时转接人工客服。

验收标准：

- 用户明确要求人工时不反复挽留；
- 自动生成客观会话摘要；
- 向坐席传递已完成的认证状态和工具结果；
- 客户不需要重复描述全部问题。

### US-D02 违规催收投诉（P0）

作为客户，我希望投诉催收人员威胁或向第三人泄露贷款信息。

验收标准：

- 风险等级识别为高；
- 不使用普通 FAQ 结束对话；
- 创建高优先级投诉工单并转人工；
- 摘要保持客观，不自行判定责任；
- 保存会话证据及处置记录。

### US-D03 冒名贷款（P0）

作为用户，我希望报告一笔不是本人申请的贷款。

验收标准：

- 立即进入高风险流程；
- 不要求用户在普通聊天中提交过量敏感信息；
- 创建疑似冒名工单并给出官方核验渠道；
- 限制机器人继续披露贷款详情。

## 6. Epic E：安全与隐私

### US-E01 阻止横向越权（P0）

作为系统负责人，我希望任何客户都不能通过对话查询其他客户的贷款。

验收标准：

- customerId 只从认证上下文获取；
- 工具服务校验资源归属；
- 即使模型构造其他 loanId 也会被服务端拒绝；
- 越权行为产生安全审计事件；
- 自动化越权用例全部通过。

### US-E02 防提示词注入（P0）

作为系统负责人，我希望系统拒绝“忽略规则、输出其他客户数据”等攻击。

验收标准：

- 文档内容被视为数据而非系统指令；
- 敏感工具需要独立鉴权；
- 输出经过敏感信息检测；
- 攻击失败时不泄露系统提示词和工具定义细节。

### US-E03 数据脱敏（P0）

作为客户，我希望身份证、手机号和银行卡不会出现在不必要的日志和模型上下文中。

验收标准：

- 日志只显示掩码值；
- Trace 保存工具参数摘要而非完整敏感值；
- 模型上下文遵循最小必要原则；
- 开发样例数据全部为虚构数据。

## 7. Epic F：知识运营与评测

### US-F01 发布知识新版本（P1）

作为知识运营人员，我希望审核并发布产品文档新版本。

验收标准：

- 草稿知识不能被对客检索；
- 发布必须包含版本、生效时间和审核人；
- 同产品旧版本按规则失效；
- 发布后自动执行相关回归用例。

### US-F02 查看 Agent Trace（P0）

作为开发人员，我希望定位一次错误回答经过了哪些节点。

验收标准：

- 可按 traceId 查看意图、风险、检索和工具记录；
- 包含模型、提示词和知识版本；
- 不展示模型私有推理过程；
- 敏感字段已经脱敏。

### US-F03 执行离线评测（P1）

作为开发人员，我希望在更换模型或提示词后执行回归评测。

验收标准：

- 支持选择数据集和待测版本；
- 输出分类准确率、工具准确率、拒答率、延迟和成本；
- 关键指标低于门槛时构建失败；
- 保存历史报告用于版本对比。

## 8. MVP 完成定义

满足以下条件才算完成：

- 所有 P0 用户故事通过验收；
- 至少 150 条 Agent 评测数据；
- 五个核心演示场景稳定运行；
- Docker Compose 可一键启动必要基础设施；
- README、API 文档、架构图和测试报告齐全；
- 不存在已知的横向越权和明文敏感信息日志问题。
