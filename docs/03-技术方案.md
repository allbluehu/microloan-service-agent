# 技术方案

## 1. 技术选型

| 层次 | 选型 | 说明 |
|---|---|---|
| 语言 | Java 21 | record、sealed class、虚拟线程等现代 Java 能力 |
| Web | Spring Boot 3.4+ | 核心应用框架；初始化时以 start.spring.io 当前稳定版钉死小版本 |
| AI | Spring AI 1.0.x GA | ChatModel 与 Embedding；业务动作由应用层确定性编排，不向模型注册 Tool Calling；要求 Spring Boot 3.4+ 与 Java 17+ |
| 安全 | Spring Security + JWT | 用户身份与接口授权 |
| ORM | MyBatis | 明确 SQL，便于展示资源归属和复杂查询 |
| 数据库 | PostgreSQL | 业务数据、全文检索和审计数据 |
| 向量库 | pgvector | 减少个人项目基础设施数量 |
| 缓存 | Redis | 会话、认证状态、限流和短期上下文 |
| 流式接口 | Spring MVC + SseEmitter | 流式回复和状态事件；选型理由见 ADR-005 |
| 迁移 | Flyway | 表结构版本管理 |
| 容错 | Resilience4j | 超时、限流、熔断和只读重试 |
| 观测 | Micrometer + OpenTelemetry | 指标与链路上下文 |
| 测试 | JUnit 5 + Testcontainers | 单元和真实基础设施集成测试 |
| 前端 | Vue 3 + TypeScript | 客户聊天和运营界面 |
| 部署 | Docker Compose | 本地一键启动 |

模型通过 Spring AI 抽象接入，具体供应商由环境变量配置。仓库不硬编码 API Key。

## 2. 架构决策

### ADR-001：采用模块化单体

首版使用一个 Spring Boot 应用承载业务模块和 Agent 模块，模块之间仅通过应用服务交互。原因：

- 个人项目更容易完成和部署；
- 保留清晰边界，未来可以拆分；
- 避免微服务通信掩盖 Agent 核心能力。

### ADR-002：采用单 Agent 受控状态机

首版不采用多 Agent。原因：

- 客服流程的角色和工具边界明确；
- 确定性路由更容易测试和审计；
- 多 Agent 会增加延迟、成本和不可预测性；
- 面试重点是可靠 Agent 工程，而不是 Agent 数量。

### ADR-003：业务数据通过工具访问

模型不能访问 Repository、数据库连接或自由 SQL。每个工具对应明确业务能力，并通过领域服务完成权限、幂等和校验。

### ADR-004：RAG 使用混合检索

产品编码、条款名称适合全文检索；口语化表达适合向量检索。因此采用 PostgreSQL FTS 与 pgvector 召回、RRF 融合、重排的流程。

### ADR-005：流式接口采用 Spring MVC + SseEmitter

不使用 WebFlux。原因：

- ORM 选型 MyBatis 是阻塞栈，与 WebFlux 混用需要额外处理阻塞隔离与调度器，复杂度不匹配项目规模；
- Java 21 虚拟线程足以支撑本规模的 SSE 并发连接；
- 项目学习重心是 Agent 编排与工具治理，不是响应式编程；
- Spring AI 阻塞式 API 的功能覆盖比响应式版本完整。

代价：放弃完整非阻塞与背压能力。对单实例、低并发的个人项目可接受；若未来需要高并发推送再重新评估。

## 4. Agent 状态机

### 4.1 状态模型

```java
public record AgentState(
        String traceId,
        String sessionId,
        Long authenticatedCustomerId,
        List<ConversationMessage> messages,
        Intent intent,
        Map<String, String> entities,
        RiskLevel riskLevel,
        AuthLevel authLevel,
        List<KnowledgeEvidence> evidences,
        ToolInvocation toolInvocation,
        Object toolResult,
        HandoffReason handoffReason,
        String finalAnswer
) {}
```

状态中不保存验证码、完整证件号或银行卡号。

### 4.2 节点

| 节点 | 职责 | 是否调用模型 |
|---|---|---|
| InputGuardrail | Bean Validation、模型输入 JSON 编码、敏感输入脱敏和长度限制；当前分散在 HTTP 与分类边界 | 否 |
| IntentClassifier | 意图与实体结构化提取 | 是 |
| RiskClassifier | 明确规则优先，可选模型补充隐晦风险；弱信号在模型故障时安全升级 | 可选 |
| RouteDecision | 根据意图与风险选择确定性路径 | 否 |
| AuthenticationCheck | Controller 从认证主体构造可信执行上下文，领域 Service 校验资源归属和身份等级 | 否 |
| KnowledgeRetriever | 混合检索与重排 | Embedding/重排 |
| ToolExecutor | AgentRouteExecutor 通过固定 switch 执行白名单业务动作 | 否 |
| ResultVerifier | 校验意图/结果类型、资源标识、金额分项、日期状态和知识引用 | 否 |
| ResponseGenerator | DeterministicResponseRenderer 基于权威结果使用固定模板组织答案 | 否 |
| OutputGuardrail | 最终回答统一执行敏感数字遮蔽、长度限制和内部实现泄漏检查 | 否 |
| HumanHandoff | 通过白名单路由幂等创建工单并使用固定模板生成交接信息 | 否 |

### 4.3 路由伪代码

```java
AgentState handle(AgentRequest request, AgentExecutionContext context) {
    SessionContext session = conversationWriter.recordUserMessage(request, context); // 短事务
    AgentState state = stateFactory.create(request, context, session);
    state = ruleRiskClassifier.apply(state);
    state = modelRiskClassifier.optionalReview(state);
    state = riskDecisionPolicy.combine(state);

    if (state.riskLevel() == RiskLevel.HIGH) {
        state = state.withIntent(HIGH_RISK_COMPLAINT);
    } else {
        state = compositeIntentDetector.orModelClassifier(state);
    }

    state = agentRouteExecutor.execute(state);       // 固定 switch，并调用确定性回答渲染器
    state = resultVerifier.verify(state);
    state = outputGuardrail.apply(state);
    conversationWriter.recordAssistantMessage(state); // 独立短事务
    return state;
}
```

`handle` 自身不持有数据库事务。真实模型、Embedding 和外部依赖调用位于事务之外；各领域业务动作自行控制
短事务。Agent Trace 使用独立事务记录，因此后续业务失败时仍保留已经发生的节点和失败原因。

## 5. RAG 设计

### 5.1 知识元数据

每个切片至少包含：

- `documentId`、`chunkId`；
- `title`、`sectionPath`；
- `productCode`、`region`；
- `version`、`effectiveFrom`、`effectiveTo`；
- `audience`：PUBLIC、CUSTOMER、INTERNAL；
- `status`：DRAFT、APPROVED、PUBLISHED、EXPIRED；
- `reviewer` 与内容校验和。

### 5.2 导入流程

```text
上传 → 病毒/格式检查 → 文档解析 → 语义切分
→ 元数据校验 → Embedding → 草稿索引
→ 召回预览 → 合规审核 → 发布索引
```

### 5.3 在线检索

1. 根据对话生成独立可检索问题；
2. 提取产品、地区和业务环节；
3. 过滤已发布且当前生效的对客知识；
4. 全文检索召回 Top 20；
5. 向量检索召回 Top 20；
6. 使用 RRF 融合；
7. 重排后保留 Top 3～5；
8. 低于阈值则澄清或转人工；
9. 回答记录实际引用的 chunkId。

### 5.4 生成约束

- 只能依据提供的 Evidence 或 ToolResult；
- 金额与业务状态不得由模型推导；
- 知识冲突时优先最新有效版本，无法消解则拒答；
- 对客答案不显示 INTERNAL 知识；
- 输出带可验证的来源标题，不伪造条款编号。

## 6. 受控业务动作设计

当前版本不使用 Spring AI Tool Calling，也不向模型注册带 `@Tool` 的方法。模型只输出受控意图和置信度，
`AgentOrchestrator` 再通过白名单 `switch` 选择应用层动作。这样可以确保模型不能自行选择金融业务方法、
不能构造客户身份，也不能绕过参数澄清、资源归属、二次认证和幂等边界。

### 6.1 业务动作清单

| 工具 | 类型 | 认证 | 幂等 |
|---|---|---|---|
| getApplicationStatus | 只读 | 登录 | 不需要 |
| getNextRepaymentPlan | 只读 | 登录＋资源归属 | 不需要 |
| getPaymentRecords | 只读 | 登录＋资源归属 | 不需要 |
| calculateEarlySettlement | 只读试算 | 二次认证＋资源归属 | 请求号用于审计 |
| createServiceTicket | 写入 | 登录 | 必须 |
| requestHumanHandoff | 写入 | 可匿名/登录 | 必须 |

### 6.2 业务动作安全

- `customerId` 从 SecurityContext 获取，不作为客户请求或模型参数；
- 模型只参与意图分类，业务动作名称、方法签名和返回结构不会发送给模型；
- `loanId`、`applicationId` 必须进行资源归属校验；
- 参数使用枚举、格式和长度约束；
- 写工具使用 `customerId + conversationId + type + relatedResourceId` 幂等键（与 `04-接口与数据模型.md` 工具契约一致）；`requestId` 是客户端请求号，SSE 重连或用户重发都会产生新值，仅用作审计与追踪字段，不参与幂等；
- 只读工具超时可以有限重试，写工具不盲目重试；
- 工具返回对客 DTO，不返回数据库实体或内部备注。

## 7. 记忆设计

### 7.1 短期会话

当前使用 PostgreSQL 持久化客户隔离的会话消息与业务槽位，前端恢复最近 100 条消息及已选择贷款、申请、产品和地区；支持显式清除槽位。Redis TTL 缓存作为未来扩展，不是当前运行依赖。

### 7.2 会话摘要

当前摘要从最近 100 条消息的确定性意图标签提取至多 5 个近期主题，按最近出现排序，不调用模型生成总结，也不复制历史金额或身份凭据。切换会话可恢复结构化业务选择；完整历史不直接发送给模型。

### 7.3 长期事实

贷款、账单、支付和工单状态每次从业务数据库重新查询，不把历史模型记忆作为事实来源。

## 8. 安全方案

### 8.1 身份与权限

- JWT 表示登录身份；
- 二次认证状态单独存储且短时有效；
- Controller、Tool 和 Service 分层校验；
- 运营后台使用 RBAC；
- 知识访问根据 audience 控制。

### 8.2 Prompt Injection

- 系统指令、用户输入、检索证据分区传递；
- 明确标记检索文档是不可信数据；
- 工具权限与模型输出无关；
- 拒绝输出系统提示词、内部规则和其他客户数据；
- 对上传文档执行恶意指令扫描；
- 安全测试集纳入每次回归。

### 8.3 敏感信息

- 手机号、身份证、银行卡数据库字段按需要加密；
- 日志与 Trace 统一脱敏；
- 不向外部模型发送完整身份证和银行卡；
- 生产概念方案中配置数据保存期和删除流程；
- 仓库只包含虚构数据和 `.env.example`。

## 9. 可靠性与幂等

- 模型调用设置超时、并发隔离和熔断；
- 检索失败时允许固定 FAQ 或人工服务降级；
- 业务系统超时时不生成业务结论；
- 写工具采用幂等表或唯一索引；
- Agent 节点保存检查点，恢复时不重复执行已成功写工具；
- 每个状态迁移校验前置状态，避免乱序推进；
- 当前 SSE 采用状态与最终答案事件；断线不自动重放，客户使用相同 messageId 显式重试。尚未提供 Last-Event-ID 事件存储与重放，详见交付文档。

## 10. 可观测性

每个请求生成 traceId，记录：

- 会话与用户掩码标识；
- 节点开始、结束、耗时和结果；
- 模型供应商、模型和提示词版本；
- 输入输出 Token 与估算成本；
- 检索 query、chunkId、分数和版本；
- 工具名称、脱敏参数、结果码和耗时；
- 最终路由、转人工原因和用户反馈。

不记录模型隐藏推理过程，只记录可审计的结构化决策结果。

## 12. 后续演进

MVP 稳定后可以演进：

- 将 Agent 服务拆为独立服务；
- 引入消息队列异步处理知识导入和离线评测；
- 为电话渠道增加 ASR/TTS；
- 引入模型路由，小模型处理分类，大模型处理复杂回答；
- 对客服工作台增加实时话术推荐与全量质检；
- 在充分评测后研究专用子 Agent，但保持统一权限和工具网关。

### ADR-006：交付界面与长会话上下文

Vue 3 + TypeScript 构建产物随 Spring Boot 发布，避免演示运行依赖额外前端进程。客户、坐席与知识治理使用独立权限边界。SSE 只发布校验后的完整答案，断线采用保留 messageId 的显式重试，不引入持久事件重放。

当前会话持久化使用 PostgreSQL；长会话增强恢复已选择实体并从最近 100 条消息提取至多 5 个确定性主题，提供清除槽位入口。早期 Redis/模型摘要设计暂不落地，避免将旧业务事实或未验证摘要带入决策。账单、支付和工单仍每轮实时查询。
